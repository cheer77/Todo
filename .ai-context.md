## 1. Project Stack
*   **Frontend**: Vanilla JavaScript (ES Modules), Vite, SCSS (Sass), `socket.io-client`.
*   **Backend**: Node.js, Express, Sequelize ORM, Socket.IO.
*   **Database**: SQLite (Local / Development), PostgreSQL (Production).
*   **PWA**: Standard Service Worker config with a `manifest.json`.

> ⚠️ **CRITICAL RULE:** Do NOT use, suggest, or introduce any frontend frameworks like React, Vue, Angular, or Svelte. This is strictly a **Vanilla JavaScript** project.

## 2. Architecture Map
The frontend is built using a modular Object-Oriented approach. No VDOM is used; direct DOM manipulation is required.
*   **`App` (`main.js`)**: The core controller. Manages all state, handles DOM event listeners orchestration, initiates API calls via Store, and renders the UI.
*   **`Store` (`Store.js`)**: The static HTTP/API client. Wraps `fetch` calls (`getTasks`, `addTask`, `deleteTask`, `updateTask`, `updateOrder`) and communicates with the Express backend.
*   **`TaskItem` (`TaskItem.js`)**: The DOM factory. Contains pure functions/methods to generate and configure the `<li>` element mapping a task, including its drag-handle, checkbox, edit/delete buttons, text logic, and timestamps.
*   **`DragDrop` (`DragDrop.js`)**: Manages the Drag & Drop logic for reordering tasks. Handles HTML5 DnD for desktop and Touch Events (with cloned visual elements) for mobile.
*   **`EditModal` (`EditModal.js`)**: Handles the animated modal dialog logic for editing existing tasks.
*   **`Tooltip` (`Tooltip.js`)**: A reusable module to display tooltips for validation errors or warnings.
*   **`Skeleton` (`Skeleton.js`)**: Renders placeholder cards during initial data fetch.

## 3. Design System & UI/UX
*   **Visual Style**: Premium **Glassmorphism**. Uses frosted-glass cards with animated gradient background globes (`.background-globes`).
*   **Typography**: The primary font is [Outfit](https://fonts.google.com/specimen/Outfit).
*   **Animations**:
    *   *Task Deletion*: Tasks should use the "evaporate" effect (CSS `.removing` class scaling down/fading and collapsing margin/padding).
    *   *Skeleton Loaders*: Used heavily on initialization to prevent layout shifts.
    *   *Modals/Tooltips*: Utilize smooth CSS-driven entry/exit transitions.
    *   *Text Expander*: Long tasks (>400 chars) use a gradient fade mask when truncated, with an animated "Show more" expand/collapse behavior.

## 4. State Management & Sync
*   **Real-Time Sync**: Every change to the database must emit a Socket.IO event (`tasks:update`) to sync all connected clients (like Trello).
*   **Data Flow**: The UI must not optimistic-update complex state without confirming with the backend or Socket event. Standard flow: Action triggered -> Call `Store` method -> Re-render `App` state / broadcast socket.
*   **Local UI State**: Features like UI filtering (All/Active/Done) should be handled instantly on the client-side, caching the response in the `App` instance to avoid unnecessary REST calls, and persisting the choice in `localStorage`.

## 5. Coding Rules & Conventions
1.  **Modules Structure**: Write code strictly in **ES Modules syntax** (`import`/`export`). No CommonJS on the frontend.
2.  **Data Manipulation**: Use ONLY existing methods of the `Store` class for manipulating backend data. Do not use direct `fetch` calls outside of `Store`.
3.  **DOM Integrity**: Abide by the existing DOM structure. Task elements MUST be instantiated as `<li>` elements using the specific CSS classes found in `TaskItem.js` (`.task-item`, `.task-content`, `.drag-handle`, `.checkbox-container`, etc.).
4.  **Error Handling**: Utilize the existing `Tooltip` system to display validation errors (e.g., empty task, exceeding the 1500 limit). Do not use native `alert()`.
5.  **Reordering Safety**: The drag-and-drop mechanism operates on DOM positioning. Backend sync of task orders uses `PUT /api/tasks/reorder/batch`.
6.  **Documentation (README.md)**: ANY time a new feature is added, or an existing architecture is significantly modified, you MUST update `README.md` to reflect these changes. The `README.md` is the primary human-readable documentation and must stay perfectly synced with the actual application features and APIs.
